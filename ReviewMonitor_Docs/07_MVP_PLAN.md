# ReviewMonitor MVP 开发计划

## 1. 开发策略

先验证平台接口，再实现端到端闭环。MVP 不追求一次性覆盖所有市场和高级分析功能。

推荐顺序：
1. 平台 API 可行性验证；
2. 数据模型和 API 基础；
3. CloudWorker 任务链路；
4. Web 评价使用闭环；
5. Dash 运营监控；
6. 稳定性、安全和开放注册。

## 2. 阶段 0：平台接口验证（1–2 天起，视平台反馈调整）

逐个平台确认：
- 是否有官方 API；
- 授权流程和所需角色；
- 可访问的评价字段；
- 是否能获取历史评价；
- 分页和增量参数；
- API 速率限制；
- 评价更新/开发者回复数据是否可读；
- 商业使用条款；
- 凭证生命周期和撤销方式；
- 火山引擎函数计算网络能否访问接口。

优先 Apple、Google、华为。小米、OPPO、vivo 先确认正式接口和商业授权，不将非官方抓取作为 MVP 依赖。

交付物：
- 每个平台 API 验证记录；
- 授权操作说明；
- 标准化字段映射；
- 错误码映射；
- 结论：可做 / 受限可做 / 暂不可做。

## 3. 阶段 1：基础平台与数据模型

任务：
- 初始化 Monorepo；
- 建立 NestJS API；
- 配置 TypeORM、MySQL migration；
- 实现 User、Workspace、WorkspaceMember；
- 注册、登录、刷新、退出；
- Workspace 权限 Guard；
- Applications、StoreConnections、StoreApps；
- 凭证加密服务；
- OpenAPI 文档；
- 基础审计日志。

验收：
- 用户注册后创建默认 Workspace；
- 不同用户无法访问彼此数据；
- 凭证加密保存且 API 不返回明文；
- Web 能完成应用和市场连接的基础管理。

## 4. 阶段 2：CloudWorker 与评价采集闭环

任务：
- 定义 Adapter 接口；
- 实现 Apple Adapter；
- 实现 Google Adapter；
- 根据验证结果实现 Huawei Adapter；
- 创建 store_sync_configs；
- 创建 review_tasks 和 attempts；
- 实现 Scheduler 函数；
- 实现 Review Worker 函数；
- 实现任务原子领取、租约、重试、恢复；
- 评价标准化和 upsert；
- 增量游标和重叠窗口；
- review_events；
- 同步状态与数据新鲜度。

验收：
- 定时器可以触发 Scheduler；
- 到期 StoreApp 生成任务；
- Worker 执行并持久化评价；
- 重复执行不产生重复评价；
- 评价更新可更新原记录；
- 任务超时后可恢复；
- 游标仅在完整成功后推进。

## 5. 阶段 3：通知与 Web 评价中心

任务：
- Notification Outbox；
- Telegram/Webhook 渠道；
- 通知规则；
- Notification Worker；
- 失败重试和去重；
- Web Overview；
- Reviews 列表和详情；
- 内部状态和备注；
- Applications 和 Stores 页面；
- 用户侧同步状态；
- 基础 Analytics。

验收：
- 新的一星/二星评价能触发通知；
- 重复采集不重复通知；
- 通知发送失败不会导致采集任务失败；
- 用户可筛选、查看、标记评价；
- 用户能看到最后同步时间和错误提示。

## 6. 阶段 4：Dash 与运营能力

任务：
- Dash Arco Design Pro 工程；
- 独立管理员认证；
- 平台 Overview；
- Users / Workspaces；
- Applications；
- Sync Tasks 列表与详情；
- Store Integrations；
- Notifications；
- System Health；
- Audit Logs；
- 手动重试任务和通知。

验收：
- 管理员可以排查任务失败；
- 能查看函数执行和任务状态；
- 手动重试有审计；
- 普通用户无法访问 Dash 管理接口。

## 7. 阶段 5：稳定性与开放注册

- 限流和安全检查；
- 凭证轮换与删除；
- 备份和恢复演练；
- 任务积压告警；
- 函数并发和数据库连接压测；
- 评价数据保留策略；
- 隐私政策、服务条款；
- 公开注册开关；
- 套餐和配额（可先手动配置）；
- 监控平台自身运行健康。

## 9. 主要风险

| 风险 | 应对 |
|---|---|
| 国内市场缺少稳定公开 API | 先验证官方渠道，不把逆向方案作为核心依赖 |
| Google API 数据不完整 | 清晰标注采集范围，不冒充总体评分 |
| 平台限流 | Adapter 级限流、并发控制、退避 |
| 函数超时 | 单任务单 StoreApp、分页续跑、时间预算 |
| MySQL 连接耗尽 | 小连接池、函数并发上限、连接释放 |
| 任务重复 | 原子领取、业务幂等、唯一约束 |
| 通知重复 | Outbox dedupe key |
| 评价数据敏感 | 最小化保存、权限控制、删除策略 |
| 产品早期成本 | 按需函数、MySQL 任务队列、不部署额外中间件 |

## 10. 交付原则

- 每个阶段必须有可运行的端到端结果；
- 不先实现复杂抽象，再寻找实际场景；
- 以官方 API 验证结果决定平台接入优先级；
- 关键业务逻辑写自动化测试；
- 数据库变更使用 migration；
- 所有异步任务具备日志、状态和幂等保障；
- 保持 Web、Dash、API、CloudWorker 独立构建与部署。

# ReviewMonitor 产品需求文档（PRD）

## 1. 产品概述

### 1.1 产品名称

ReviewMonitor（暂定名，工作名称）。后续允许更换品牌名，不影响代码中的业务概念与技术架构。

### 1.2 一句话定位

面向独立开发者和小型 App 团队的应用市场评价监控 SaaS，帮助用户集中查看多个应用市场的评价，及时发现差评与异常反馈，并持续了解用户对产品的真实声音。

### 1.3 产品愿景

开发者不必每天登录 Apple、Google 或各家 Android 应用市场后台，也能及时掌握新评价、差评和评分变化。ReviewMonitor 负责持续采集、统一整理、异常提醒，并逐步提供 AI 评价分析能力。

### 1.4 核心价值

1. **集中管理**：多个应用、多个应用市场的评价统一查看。
2. **及时发现**：新差评和短期差评集中出现时及时通知。
3. **持续监控**：云端定时采集，用户关闭浏览器或电脑关机不影响任务。
4. **处理跟踪**：记录评价处理状态、内部备注和处理历史。
5. **数据洞察**：观察评分趋势、版本反馈和高频问题；后续引入 AI 分类与总结。
6. **采集透明**：展示最后成功同步时间、采集失败和授权异常，避免用户误以为数据实时或采集正常。

## 2. 目标用户与典型场景

### 2.1 目标用户

- 独立 App 开发者；
- 小型移动应用工作室；
- 同时维护多个应用或多个市场版本的开发团队；
- 需要集中关注用户反馈的产品经理或运营人员。

### 2.2 核心场景

**场景 A：错过差评**

开发者忙于开发或运营，数天没有登录应用市场后台。期间出现一星、二星评价，直到很久以后才发现。ReviewMonitor 应持续采集并及时通知。

**场景 B：多市场分散**

同一个应用同时发布在 App Store、Google Play、华为、小米、OPPO、vivo 等市场，评价入口和后台各不相同。用户希望在一个界面集中查看。

**场景 C：了解版本问题**

某个版本发布后，用户反馈闪退、登录失败或支付问题。用户需要按应用版本、评分、时间、市场筛选评价，识别集中出现的问题。

**场景 D：确认采集服务正常**

用户需要知道每个市场最近一次成功采集时间、最近错误、授权是否有效，避免监控服务本身停止工作却无人察觉。

## 3. 产品范围

### 3.1 MVP 必须实现

- 注册、登录、退出登录；
- Workspace 创建与基础管理；
- 多应用管理；
- 一个应用绑定多个市场条目；
- 市场连接与凭证管理；
- Apple App Store、Google Play 的首批官方 API Adapter；
- 华为/鸿蒙官方接口验证与可运行 Adapter（以接入验证结果为准）；
- 评价增量采集、标准化、去重、更新；
- 评价列表、详情、筛选、排序、分页；
- 评价内部处理状态：未处理、处理中、已解决、已忽略；
- 内部备注；
- 一星、二星评价通知；
- Telegram 或通用 Webhook 通知渠道；
- 采集任务状态、最后同步时间、失败原因；
- 基础统计：评价量、评分分布、平均评分（仅基于实际采集到的数据并明确口径）；
- 多租户数据隔离和凭证加密。

### 3.2 MVP 暂不实现

- 自动代表开发者回复应用市场评价；
- 完整客服工单系统；
- 应用内 SDK；
- 全网社交媒体舆情；
- 复杂团队审批流；
- 多层级组织架构；
- AI 自动回复并自动发布；
- 独立桌面应用；
- 独立移动端 App；
- ClickHouse 等分析型数据库；
- Redis/BullMQ 等额外中间件。

### 3.3 后续阶段

- AI 评价分类、情感/主题归类；
- 重复问题检测与问题聚类；
- AI 周报、版本反馈总结；
- 回复建议（由用户确认后使用）；
- 团队成员与协作；
- 更多通知渠道：Email、飞书、企业微信、Web Push；
- 评分与版本趋势分析；
- 移动端 Flutter 客户端；
- 付费套餐、配额、账单和用量统计。

## 4. 产品结构与导航

### 4.1 Web 用户端

建议主导航：

- Overview：总览；
- Reviews：评价中心；
- Applications：应用管理；
- Stores：市场连接与授权；
- Notifications：通知规则与通知渠道；
- Analytics：基础分析；
- Settings：个人资料、Workspace、成员与安全设置。

MVP 可将部分低频页面收纳在 Settings 中。

### 4.2 Dash 管理运营端

Dash 是独立部署的内部运营和系统监控控制台，不是普通用户的第二套业务后台。

建议导航：

- Overview：平台整体运行概况；
- Users & Workspaces：用户和 Workspace 管理；
- Applications：平台内应用与市场绑定概况；
- Reviews：采集数据量与数据质量概况；
- Sync Tasks：任务队列、执行记录、失败重试；
- Store Integrations：各市场 Adapter 状态与错误分布；
- Notifications：通知发送成功率、失败记录；
- System Health：函数执行、数据库连接、定时触发健康情况；
- Audit Logs：管理员操作审计。

Dash 访问必须有独立管理员权限，不向普通注册用户开放。

## 5. 用户与权限模型

### 5.1 核心实体

- User：登录身份；
- Workspace：业务数据隔离边界；
- WorkspaceMember：用户与 Workspace 的成员关系；
- Role：owner、admin、member（MVP 可先实现 owner；表结构预留其他角色）。

### 5.2 权限原则

- 一个用户可加入多个 Workspace；
- 一个 Workspace 可有多个成员；
- 所有业务数据必须带 `workspace_id` 或通过所属实体关系验证 Workspace；
- API 必须从认证上下文获取用户身份，并验证其 Workspace 成员关系；
- 不允许仅凭客户端传入的 `workspace_id` 就访问数据；
- 平台管理员权限与 Workspace 用户权限分离。

## 6. 功能需求

### 6.1 账号与 Workspace

**注册**
- 邮箱 + 密码注册；
- 邮箱验证能力预留；初期可根据邮件服务资源决定是否强制验证；
- 密码使用安全哈希算法保存，禁止明文存储；
- 注册成功后创建默认 Workspace。

**登录**
- 邮箱密码登录；
- 登录失败给出通用错误，不泄露账号是否存在；
- 支持退出登录；
- Token 过期后要求重新认证或刷新。

**Workspace**
- 查看和切换 Workspace；
- 修改 Workspace 名称；
- 创建 Workspace（套餐限制可后续增加）；
- Owner 可管理成员（团队协作可后续完整实现）。

### 6.2 应用管理

应用字段建议：
- 名称；
- 图标 URL；
- Bundle ID / Package Name；
- 平台类型；
- 描述（可选）；
- 状态；
- 创建时间。

一个 Application 可关联多个 StoreApp。StoreApp 表示某个具体市场中的应用条目，包含市场类型、市场侧 ID、国家/地区、应用链接、同步配置等。

用户可以：
- 新建应用；
- 编辑应用资料；
- 绑定/解绑市场条目；
- 启用/暂停某个市场的评价监控；
- 查看每个市场最近同步时间和状态。

### 6.3 市场授权与连接

每个市场连接属于 Workspace，凭证加密保存。

- Apple：按官方 App Store Connect API 授权流程配置 Issuer ID、Key ID、API 私钥等；
- Google：按 Google Play Developer API 的 Service Account / 授权流程配置；
- 华为：按官方开放平台当前授权方式配置；
- 小米、OPPO、vivo：先验证是否有正式、可持续、允许商业使用的接口；不得将逆向、抓包或模拟登录作为产品基础能力。

安全要求：
- 私钥和 Secret 不返回前端；
- 凭证写入时加密；
- 日志不得打印凭证；
- 支持测试连接；
- 支持禁用、更新、删除连接；
- 授权失效时产生可见错误和通知。

### 6.4 评价中心

列表展示：
- 评分；
- 评价标题和正文；
- 作者（平台提供时）；
- 应用；
- 市场；
- 国家/地区；
- 应用版本；
- 评价创建时间；
- 最近更新时间；
- 内部处理状态；
- 官方回复状态（如平台数据可用）。

筛选：
- 应用；
- 市场；
- 评分；
- 时间范围；
- 处理状态；
- 国家/地区；
- 应用版本；
- 关键词。

详情页展示：
- 完整评价内容；
- 来源市场；
- 原始评价时间与最近更新时间；
- 版本、设备、系统等平台可提供的信息；
- 内部备注；
- 状态变更历史；
- 官方回复内容与时间（若 API 可获取）。

内部处理状态与市场官方回复状态必须是两个独立概念。

### 6.5 评价采集

- 按市场和应用绑定关系分别调度；
- 采用增量同步、分页游标和重叠时间窗口；
- 唯一键建议 `(store_app_id, external_review_id)`；
- 对平台允许修改的评价，重复窗口中检查并更新已有记录；
- 只有完整成功的同步才推进同步游标；
- 部分失败不得错误推进游标；
- 记录每次同步开始、结束、获取数量、新增数量、更新数量、错误和耗时；
- 展示最后成功同步时间，不宣称平台数据实时。

初始建议频率：Apple / Google 约 15 分钟；华为约 15–30 分钟；其他市场按正式 API 能力、平台限流和函数成本决定。频率是内部调度目标，不构成对平台数据到达时间的承诺。

### 6.6 通知

MVP 优先：
- Telegram；
- 通用 Webhook。

默认规则建议：
- 1 星、2 星新评价：即时通知；
- 3–5 星：暂不即时通知，可在后续增加摘要；
- 连续采集失败：通知；
- 授权失效：通知；
- 短时间差评集中出现：后续阶段实现。

通知要求：
- 同一事件同一渠道避免重复发送；
- 通知失败独立重试；
- 通知失败不回滚评价数据；
- 保存发送状态、错误、重试次数和发送时间；
- Webhook 应支持签名或共享密钥校验。

### 6.7 Analytics

MVP 基础统计：
- 评价总数；
- 时间范围内新增评价数；
- 评分分布；
- 采集到的评价平均评分；
- 各应用/市场评价量；
- 最近同步时间。

统计口径必须说明：Google 官方 Reviews API 等平台可能只返回部分评价（例如只返回带文字的评价），因此不能把采集样本平均分当作平台官方总体评分。平台官方评分应在可可靠获取时单独展示，并标注来源和更新时间。

## 7. 关键业务规则

1. 一个应用可以绑定多个市场；每个市场条目独立授权、独立采集配置。
2. 评价唯一性由市场应用 + 外部评价 ID 保证。
3. 采集任务与通知任务分离。
4. 评价入库成功后再生成通知事件。
5. 评价处理状态是 ReviewMonitor 内部状态，不修改市场原始评价。
6. 用户解绑市场时停止后续调度；历史评价按产品数据保留策略处理。
7. 用户删除 Workspace 时，必须按数据删除策略清理或匿名化相关数据及凭证。
8. 任何平台接入都必须遵守平台 API 条款、速率限制、数据使用和隐私要求。

## 8. 非功能需求

- 安全：凭证加密、密码哈希、访问控制、审计；
- 可靠性：任务幂等、失败重试、租约回收、Outbox；
- 可观测性：结构化日志、任务运行记录、错误码、最后成功同步时间；
- 性能：列表分页，避免一次返回大量评价；索引覆盖常用筛选；
- 可维护性：Adapter 隔离平台差异，业务逻辑不依赖具体平台 SDK；
- 可扩展性：多租户、多个市场、多客户端共用 API；
- 成本：MVP 使用函数按需执行和 MySQL，不引入常驻 Worker 和额外中间件。

## 9. MVP 验收标准

- 用户可注册、登录并创建默认 Workspace；
- 用户可创建多个应用并绑定市场条目；
- 至少 Apple、Google 具备经过验证的可运行采集流程；华为按官方接口验证结果纳入首期或紧随其后；
- 同一评价重复拉取不会产生重复记录；
- 评价更新可更新原记录并留下必要事件；
- 一星/二星评价可触发通知，重复任务不会重复发送同一事件；
- 采集任务失败可重试，超时任务可回收；
- Web 能展示评价列表、详情、筛选和处理状态；
- Web 能展示最后同步时间和采集错误；
- Dash 能查看任务、失败、平台接入和通知状态；
- 不同 Workspace 之间无法读取彼此数据；
- 凭证加密保存，前端和日志不可见明文；
- 评价数据和官方总体评分的统计口径不混淆。
